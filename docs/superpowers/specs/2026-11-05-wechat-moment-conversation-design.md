# 微信对话式说说发布设计

## 背景

AstrBot BlogWriter 已支持在微信 ClawBot 私聊中创建说说会话、接收后续文本与图片，并通过 GitHub Contents API 写入博客仓库。当前入口主要依赖 `/动态`、`/发布` 等命令。本设计在保留现有命令的前提下，增加自然对话式的草稿创建与编辑流程。

博客由 GitHub Pages 托管。插件提交内容后触发 GitHub Actions 构建；构建成功后内容才会出现在网站，不承诺即时上线。

## 目标

- 在微信 ClawBot 私聊中直接发送文字，开始撰写一条说说。
- 允许连续发送文字与图片，机器人持续维护并回显当前草稿。
- 提供无需 AI 的可预测编辑操作：追加内容、重写草稿、撤销上一条、预览。
- 只有用户明确发送“发布”才提交到 GitHub。
- 失败时保留草稿，反馈失败原因与可重试状态。
- 保持 `/动态`、`/发布`、`/取消`、`/状态` 等旧命令兼容。

## 非目标

- 不读取用户与其他联系人的聊天，不接入任意微信聊天窗口。
- 不让 AI 自由推断编辑意图，不引入模型费用或模型错误导致的内容改写。
- 不自动提交或自动部署。
- 首期不改变网站说说展示、内容格式、图床或部署架构。

## 用户流程

1. 用户在已绑定的 ClawBot 私聊中发送第一段普通文字。
2. 插件仅对已授权用户的私聊创建说说草稿，并回复草稿已建立及当前内容摘要。
3. 用户继续发送文字时，内容追加为新的段落；发送图片时，沿用现有媒体下载和图床上传流程。
4. 用户可以发送“预览”查看将要发布的正文；发送“重写：新内容”整体替换文字草稿；发送“撤销上一条”删除最近追加的文字段落或最近一张图片。
5. 用户发送“发布”后，插件校验草稿、写入 `src/content/动态/YYYY/MM/`，再回复提交结果和博客链接。
6. 用户发送“取消”放弃草稿。沿用现有会话超时和单用户单会话规则。

首次普通消息自动成为草稿的范围仅限插件已经识别为私聊且发送者在白名单中的 ClawBot 消息。群聊、未授权用户、其他平台和插件命令不得意外创建草稿。若 AstrBot 事件无法可靠区分私聊与群聊，则不能启用自动开稿，需退回显式“说说：内容”触发。

## 状态与消息判定

- 没有活动会话时：现有插件命令按原逻辑处理；普通文字仅在允许的私聊中开启 `moment` 草稿。
- 有活动说说会话时：精确匹配的控制短语优先处理，其余普通文字追加到草稿；图片继续走已有收集路径。
- 控制短语应在清理空白后做完整匹配，不能把普通正文中的“发布”等词误判为命令。
- 发布处理需防重复触发；GitHub 写入成功后才清理会话，失败则保留草稿供重试。
- “撤销上一条”需要以会话消息项为单位记录文本和媒体，避免仅修改最终 Markdown 时无法准确回滚。

## 安全与权限

- 继续使用插件现有用户白名单；未授权用户不得创建、查看或操作草稿。
- 自动开稿限定为一对一私聊，不在群聊中捕获普通消息。
- 普通消息正文、图片和发布动作均不发送给第三方 AI 服务。
- 发布是唯一提交边界；预览、追加、重写、撤销均不访问 GitHub 写接口。

## 错误处理

- 图片下载或图床上传失败时，告知具体失败项，不丢失已收集的文字与其他图片。
- GitHub 查询、文件写入或网络失败时保留会话，允许用户重试“发布”。
- 草稿为空时拒绝发布并说明如何补充内容。
- 同日已有说说时沿用现有冲突重试与文件名后缀规则，不覆盖旧内容。
- 回复明确区分“已提交，正在构建”和“网站构建完成”；插件只能确认提交成功，不能声称 Actions 已部署成功。

## 实现范围与验证

- 主要改动：`plug-in/AstrBot/astrbot_plugin_blog_writer/main.py`、`blog_writer_core.py` 及相应测试。
- 由于 `plug-in/` 被主仓整体忽略，插件改动需按本地备份和打包规范另行保存、重打包，不能依赖主仓提交。
- 先为消息路由、私聊限制、追加/重写/撤销、预览、显式发布和失败保留编写回归测试，再实现行为。
- 按 `CLAUDE.md` 要求运行插件完整 unittest；同时检查 ZIP 内中文文件名及插件版本信息。
- 完成功能后同步维护 `CLAUDE.md` 和 `src/content/更新日志/`，并按项目收尾规范验证。

## 待实现前确认的技术门槛

- 核实当前接入的个人微信适配器事件对象能否稳定识别私聊与群聊。
- 核实草稿会话存储结构能否表达“文字段落/图片”有序项目；若不能，采用只用于说说会话的轻量项目列表，不迁移其他内容类型。
- 确认插件成功提交后返回的信息与 GitHub Pages 工作流一致，不沿用旧 README 中的 EdgeOne 描述。
