先说结论：大多数表格组件的二次封装不是「设计得不够好」，而是**一开始就封错了层**。

封错层的标志很好认——组件越更新越厚，页面上的 `<MyTable>` 标签越来越长，长到需要单独开一行 `:config="tableConfig"`，而这个 config 对象每个页面写的都不一样。到这一步，封装已经不减少代码了，它只是把代码从页面挪到了一个更难读的地方。

## 一个典型的膨胀过程

最初的诉求通常只有一句：全站的表格都要有分页、都要统一列宽、都要有空状态。于是第一版大概长这样：

```vue
<MyTable :columns="columns" :data="list" :loading="loading" />
```

这个版本几乎没有争议。它封的是三件确定的事：布局、分页器的位置、空态文案。改动少，出问题也容易定位。

第二个月，需求来了：有的表格要支持行选择，有的要支持展开行，有的要远程排序。于是加了三个 props。再下个月，某个页面需要自定义操作列，于是加了 `actionColumn` 配置；又一个页面需要在单元格里塞进度条，于是 `columns` 里多了 `render` 字段，而这个字段的值是一个函数或者一段 JSX 字符串——具体是哪种，取决于当时谁写的。

三个月后，这个组件的 props 大概是这样：

```text
columns / data / loading / height / maxHeight / stripe / border
rowKey / selection / selectionType / selectable
expandable / expandRender / treeProps
pagination / pageSizes / pageLayout / remote / total
sortable / sortRemote / defaultSort
summary / summaryMethod / spanMethod
actionColumn / actionWidth / actionFixed
emptyText / emptySlot / errorText
density / size / align / headerAlign
onRowClick / onRowDblclick / onCellClick
exportable / exportName / exportFormatter
```

四十个左右，每个都有人用，每个都能说清楚为什么存在。这时候你没法删任何一个 prop，因为它们都已经「有主」了。

## 问题的根源不在数量

很多人以为这是「配置项加太多」的问题，于是做一轮重构，把 props 收进一个 `options` 对象——代码整洁了，但难度没变。因为真正的问题不是 props 多，而是**组件把「能力」和「策略」封在了一起**。

- 能力：渲染一个表格、支持虚拟滚动、支持列固定。这是表格库给的，稳定，不需要每个页面重新决定。
- 策略：什么时候展示空态、操作列放左边还是右边、分页器要不要显示总数、导出文件名怎么起。这是业务决定的，每个页面不一样。

第一版封装只碰了策略里最通用的几条。后来每个新需求都把一条新策略塞进组件，组件就变成了一个「所有页面策略的并集」。并集的问题是：它对你正在写的这个页面，永远是过量的。

判断标准很简单：**新增一个需求时，改的是组件还是页面。**

如果改组件，说明这条需求被当成了通用能力；如果长期看只有一两个页面用得上，那它其实是某个页面的策略，被错误地上升到了组件层。这类「错误的上升」积累十几条之后，组件就没人敢动了——不是不能改，是改之前得先确认二十个页面不受影响。

## 分三层，比减少 props 更有效

我的做法是把一个表格拆成三层，每层只回答一个问题。

**第一层是契约。** 只关心三样东西：数据从哪来、列怎么定义、行上能做什么。这一层的 props 应该是稳定的，半年不新增也正常。

```vue
<MyTable
  :columns="columns"
  :loader="loadRows"
  :actions="rowActions"
/>
```

注意 `loader` 是个函数而不是 `data`。这个改动看起来只是换个写法，实际解决了两个老问题：加载状态由组件自己管，页面不用再维护 `loading`；翻页、排序、筛选统一走同一个入口，不用每个页面各写一遍 `handlePageChange`。

**第二层是表现。** 密度、斑马纹、边框、高度，这些是纯视觉的，允许通过 CSS 变量或者一个 `appearance` 对象集中覆盖。这一层不要做成 props，做成变量。因为表现类需求的特点是「全局一致、局部例外」，用变量覆盖一行 CSS 就够了，做成 prop 反而要在每个页面都传一遍。

**第三层是逃生舱。** 这一层是最容易被忽略、但决定了组件能不能活过一年的东西：允许在必要时拿到底层实例，或者直接用插槽接管某一块渲染。

```vue
<MyTable :columns="columns" :loader="loadRows">
  <template #cell:progress="{ row }">
    <ProgressBar :value="row.progress" />
  </template>
</MyTable>
```

有了逃生舱，那些「只有这一个页面需要」的怪异需求就不必变成 props，页面自己解决，组件保持干净。反过来，如果一个需求连续三个页面都要写逃生舱，那它才真的该升级成能力。

这个判断顺序很重要：**先允许绕过去，再统计绕过次数，最后才决定要不要收编。** 反过来做，就是前面那四十个 props 的由来。

## 用 vxe-table 时特别要注意的一点

`vxe-table` 这类库本身已经很重了，二次封装时最容易犯的错是「再包一层反射」——把它的 props 一个个透传出来。

```vue
<!-- 不要这样 -->
<MyTable :border="border" :stripe="stripe" :show-overflow="showOverflow" ... />
```

透传层的问题是它没有增加任何信息，只增加了一次维护成本：底层库升级改了参数名，你得跟着改一遍；底层库新增了能力，你得手动放行。更糟的是它让调用方以为这是「你的组件的能力」，出问题时先来找你，而其实只是透传没写对。

正确的做法是用 `v-bind="$attrs"` 加 `inheritAttrs: false` 让不认识的属性直接落到根节点，再用 `expose` 暴露少数几个确实需要的方法。这样底层库的能力天然可用，你只需要维护自己新增的那部分。

```vue
<script setup>
defineOptions({ inheritAttrs: false })

const tableRef = ref()
defineExpose({
  refresh: () => loadRows(),
  clearSelection: () => tableRef.value?.clearCheckboxRow(),
})
</script>

<template>
  <vxe-table ref="tableRef" v-bind="$attrs" :data="rows" />
</template>
```

暴露的方法不要多，五个以内。每多一个，就多一个别人可以绕过你的约束直接改状态的入口。

## 什么时候不该封装

还有一种情况值得单独说：**只有一个页面用的表格，不要封装。**

封装的价值来自复用，而复用的前提是「第二个使用方出现」。在只有一个使用方的时候封装，你其实是在猜第二个使用方长什么样，猜错的概率接近百分之百——因为你对第二个页面的全部了解，来自一句「以后别的页面也要用」。

我现在的做法是：第一个页面直接写，写完之后如果第二个页面出现了，把两边的差异列出来，差异在三处以内才封装，超过三处就先复制一份。复制确实不优雅，但它的成本是可见的、可控的；错误封装的成本是隐性的，会在半年后以「这个组件没人敢改」的形式出现。

## 收尾

表格组件之所以难封，是因为它同时承担了三种角色：数据的展示器、交互的容器、业务规则的落点。这三种东西的变化频率差了不止一个数量级，硬塞进一个 API 里，就只能取它们变化频率的最大值——也就是业务规则那个频率，于是组件永远在改。

分层不是为了好看，是为了让变化频率不同的东西各自有地方待着。契约层半年动一次，表现层用变量兜住，逃生舱负责接住那些「就这一次」的例外。

判断一个封装好不好，我只看一件事：**新来的同事写一个新页面时，是照着文档传参数，还是照着另一个页面抄。** 如果是后者，说明这个组件的 API 没有表达清楚它自己的能力，它只是一个恰好能跑的模板。
