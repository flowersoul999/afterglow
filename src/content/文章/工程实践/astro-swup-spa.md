给静态站加 SPA 导航，代码量不大：引入 Swup，指定容器，加个淡入淡出。半小时能跑起来。

真正花时间的是接下来的两周。上线之后陆续出现的症状大概是这样：

- 首页进文章页，文章里的复制按钮点了没反应
- 从文章页返回列表，列表的筛选还停留在上一页的状态
- 同一个按钮点一次触发两次
- 滚动监听越来越卡，切十次页面之后滚动明显掉帧
- 某个页面的样式在直接访问时正常，从别的页面跳进来就丢了

这些症状分布得很散，看起来像五个不同的 bug。它们其实是同一个 bug 的五个侧面。

## 只有一条规律

整页加载时，浏览器的模型很简单：导航 = 卸载旧文档 + 加载新文档。所有 JS 执行环境、事件监听、定时器、闭包，全部跟着文档一起销毁。你写什么都不会泄漏，因为根本没有「之后」。

Swup 改掉了这个前提。它拦下链接点击，用 fetch 拿新页面的 HTML，然后把容器里的内容替换掉。于是：

- DOM 节点被销毁了
- `window`、`document` 没有销毁
- 你注册在 `document` 上的监听器还活着，而且指向已经不存在的节点
- 你在模块顶层写的初始化代码不会重跑

一句话概括：**DOM 的生命周期变短了，但 JS 作用域的生命周期没变。**

后面所有问题都是这句话的推论。

## 第一类：脚本根本没执行

最常见的现象是新页面的交互全废，刷新一下就好。

原因通常不是 Swup 的 bug，而是脚本被放在了替换区域之外。Swup 只替换容器内的 DOM，容器外的 `<script>` 标签在首次加载时执行过一次，之后无论怎么跳转都不会再跑。

在 Astro 里这个位置很具体：需要随页面切换重新执行的脚本，必须放在 `MainGridLayout` 的 slot 里，也就是最终落在 Swup 容器内部。放在 `Layout` 的 `<head>` 或者 `</body>` 前，它只对首屏有效。

同理，写在组件顶层的初始化代码（比如 `document.querySelector('.toolbar')?.addEventListener(...)`），在跳转之后不会再执行，因为它所在的模块只求值一次。

判断方法很直接：在脚本第一行打一条日志，跳转一次看有没有输出。没有输出就是执行时机问题，不用往下查绑定逻辑。

## 第二类：监听器越积越多

比「不执行」更隐蔽的是「执行太多次」。

假设你有一段代码，每次进入列表页都给 `document` 加一个 keydown 监听：

```js
document.addEventListener("keydown", handleSearch);
```

首屏进入，一个监听器。跳到详情页，`document` 没变，监听器还在。再跳回列表页，又加一个。三次之后，你按一次 `/`，搜索框获得三次焦点；十次之后，滚动开始卡。

这类泄漏在整页加载下不可能发生，所以写的时候完全没有警觉。而在 SPA 下它几乎必然发生，因为 `document` 是全局的，而你的初始化代码是「每进一次页面跑一次」。

修法只有一种：**凡是绑在容器外的监听器，必须在离开时解绑**。用 `AbortController` 最省事，一个 signal 管一批：

```js
let ac = new AbortController();

function mount() {
  ac = new AbortController();
  document.addEventListener("keydown", onKey, { signal: ac.signal });
  window.addEventListener("scroll", onScroll, { signal: ac.signal });
}

function unmount() {
  ac.abort();
}
```

要点是每次 mount 都新建一个 controller，而不是复用同一个。复用的话，第一次 abort 之后信号就永久失效，后面再挂监听器会立刻被取消。

如果是 Svelte 组件，`onMount` 返回的清理函数在组件销毁时会执行，这条路是安全的。危险的是那些手写在 `.astro` 里、直接操作 `document` 的脚本——它们不受任何框架生命周期管理，全靠自己收拾。

## 第三类：单例被初始化两次

有些东西天然只能有一份：音乐播放器、搜索弹窗、全局的 tooltip 容器、图表实例。

整页加载时，「一份」由文档保证——每次都是新的文档，旧的随文档消失。SPA 下这条保证没了，于是你会遇到两个播放器同时出声，或者两个搜索框叠在一起。

常见写法是在脚本里判断一下元素存不存在：

```js
if (!document.querySelector("#player")) {
  initPlayer();
}
```

这个判断在「DOM 被完全替换」时是有效的，但如果容器里的内容只被部分替换，或者同一个组件在一页里出现两次，它就会失效。更稳的做法是把状态挂在 `window` 上，用显式的标记位：

```js
if (!window.__playerInited) {
  window.__playerInited = true;
  initPlayer();
}
```

初看很脏，但这是唯一一个不依赖 DOM 的存在性判断。仓库里这类 guard 变量已经有一批，命名统一用 `__xxx` 前缀，好处是出问题时能全局搜出来。

## 第四类：拿着过期的 DOM 引用

这一类最阴，因为它不一定报错。

```js
const panel = document.querySelector(".side-panel");

document.querySelector("#open-btn").addEventListener("click", () => {
  panel.classList.toggle("is-open");
});
```

整页加载下这段代码永远正确，因为 `panel` 和按钮在同一次文档生命周期里。SPA 下跳转一次之后，`panel` 指向的节点已经被移出文档，`classList.toggle` 作用在一个游离节点上——不报错，只是页面上什么也没发生。

更糟的情况是它报错但报得莫名其妙：`Cannot read properties of null`，而你明明看到元素就在页面上。因为那是新的元素，你手里的是旧的。

原则很简单：**不要在模块作用域缓存 DOM 引用**。要么在每次需要时重新 `querySelector`（性能可以忽略，选择器命中是毫秒级），要么把引用存在随页面一起重建的局部作用域里。

## 正确的注册方式

上面四类问题对应四种修法，但它们都需要一个共同的前提：知道「新页面已经就位」这个时刻。

Swup 提供了这个时刻，`content:replaced` 事件。页面级的初始化逻辑应该挂在这里，而不是写在模块顶层：

```js
document.addEventListener("swup:content:replaced", () => {
  mountPageFeatures();
});
```

这里有个容易踩的点：这个监听器本身是绑在 `document` 上的，如果它所在的脚本被重复执行，就会重复注册。所以注册这一步要做幂等——用 guard 变量，或者只在真正的入口脚本里注册一次。

还有一条经验：**不要把所有初始化都塞进一个全局的 `mountAll()`**。页面 A 的功能在页面 B 上也会被执行一遍，然后在 B 的选择器上返回 null，静静地什么也不做。时间久了没人知道哪些代码在哪个页面跑。按功能拆成独立的小模块，每个模块自己判断「我该不该在这一页生效」，比一个中心化的初始化函数好维护得多。

## 为什么这类问题特别难查

因为它们全都**不报错**。

监听器泄漏不报错，只是越来越卡；单例重复不报错，只是两个声音；DOM 引用过期有时不报错，只是没反应。而你排查时会发现「刷新一下就好了」——这句话本身就是最强的线索：刷新能好，说明问题出在「第二次进入」，而不是这段代码本身写错了。

所以我的排查顺序固定成这样：

1. 刷新后正常、跳转后异常 → 生命周期问题，不用看业务逻辑
2. 跳转后无任何反应 → 先确认脚本执行了没有（打日志）
3. 有反应但行为叠加 → 查监听器有没有解绑
4. 报 null 但元素明明在 → 查有没有缓存 DOM 引用

按这个顺序，大部分问题在第二步就能定位，不用读完整个文件。

## 一句总结

整页加载的模型是「环境跟着页面走」，SPA 的模型是「页面跟着环境走」。一旦接受了后者，很多写法要反过来：初始化要在正确的事件里做，清理要显式写，全局状态要有 guard，DOM 引用不要跨生命周期持有。

这些都不是 Swup 的问题，是这个模式本身的代价。它换来了无刷新的体验，代价是你得自己承担浏览器原本替你做的事——销毁。
