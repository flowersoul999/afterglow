让 AI 直接写页面，它交给你的是一份能跑的代码，和一张你不太敢认的脸。

你说「二次元风格」，它理解成紫色渐变加圆角卡片加居中大标题。每一条单看都合理，拼起来不是你要的站。然后开始纠：字大一点、紫色别这么艳、卡片别这么圆。改到第五轮才发现，问题根本不在细节，在结构。

这不是模型笨。是中间没有东西可以拿来比。

## 一篇讲流程的文章

前几天看到 MmzMing 写的《纯AI，零人工》，讲他用 AI 搭 Astro 博客的流程。核心五步：

1. AI 定整体风格
2. 写一个原型图 `.html`
3. AI 生成代码规范
4. 代码必须跑红绿测试
5. 持续优化

他把配置仓库也开源了，里面是十来个 Claude Code 的 skill。所谓 skill，就是每个目录一个 `SKILL.md`，用自然语言写清楚「这类活该怎么干」，模型遇到相关任务时自己去读。

我把这 16 个技能搬进了自己每天用的工具，又补了 2 个。搬的过程不难，麻烦的是中间撞上两个坑，两个都不报错。

## 坑一：名字对不上，技能就在那儿但用不了

技能目录长这样：

```text
skills/
  ai-animation/
    SKILL.md
  api-doc-w/
    SKILL.md
```

`SKILL.md` 开头有一段 frontmatter：

```yaml
---
name: ai-animation
description: 使用 AI 生成 HTML 演示动画的自动化工作流……
---
```

我挨个核对时发现两个对不上：`ai-animation/` 里写的 `name` 是 `AI-Animation`，`api-doc-w/` 里写的居然是 `java-api-doc-writer`，跟目录名都没关系。

这类不一致我没法拍胸口说它一定导致加载失败，但它是典型的静默失败来源：索引按目录名建，`name` 只是声明，两边不一致时，最坏的情况不是报错，而是技能「看着在列表里，用的时候对不上号」。你会以为是 AI 不会用这个技能，其实是它压根没读进来。

统一成本为零，所以统一了。顺手写了段循环把这件事变成可复检的，顺便查另外三件事：首行是不是 `---`、有没有 `description`、`description` 是不是短得离谱。

## 坑二：流程的终点指向一个不存在的技能

第二个坑更隐蔽，也更有意思。

`brainstorming` 这个技能的结尾是这么写的：

> **The terminal state is invoking writing-plans.** Do NOT invoke frontend-design, mcp-builder, or any other implementation skill.

问题是，整个仓库里没有 `writing-plans` 这个目录。

这个坑的性质跟第一个完全不同。第一个是「可能不生效」，这个是**确定会断**，而且断得极其安静：`brainstorming` 正常触发，问需求、提方案、写设计文档，前面每一步都走得通，走到最后一步——它说「下一步该调 writing-plans 了」——然后什么也不会发生。

你不会收到任何错误提示。你只会觉得这个流程好像有点戛然而止。

而 `brainstorming` 的触发描述写的是 `You MUST use this before any creative work`，范围大到几乎必然被触发，所以这个断点迟早会踩上。

我按它的要求补了一个 `writing-plans`：把已批准的设计文档拆成可执行任务，每个任务必须写清「改哪个文件、做什么、怎么验证」。其中最硬的一条是不许写占位符——TODO、「此处补充」、「具体实现略」全部禁止，写不出细节说明设计没想清楚，退回去重想。

顺带记一笔：这段 frontmatter 里的 `description` 不是给人看的介绍，是给模型判断「这活该不该用我」的路由表。它写得太窄，技能永远调不出来；写得太宽，什么活都往上套。`brainstorming` 那句 `MUST` 就属于过宽，按字面执行的话，改个按钮颜色都得先走一轮「提问 → 提方案 → 写设计 → 等批准」。这条我还没改，先留着观察。

## 这套流程里真正值钱的东西

五步里我认为只有一步是不可替代的：**做原型**。

原型是一个单文件 `.html`，CSS 内联，双击能在浏览器里打开，不接构建、不引组件、不要数据。它的唯一用途是跟参考图并排比。

它的价值不在「好看」，在于它是整条链路上唯一一个**错得起**的地方。原型画歪了，删掉重画，成本是二十分钟。跳过它直接把视觉改动写进项目，画歪了要回滚组件、清理样式、重启 dev server、确认没有残留影响，成本是半天，还要担着「别的地方被顺手改坏了」。

所以这条线不能省：先在便宜的地方出错，再往贵的地方搬。

原文里还有一段我印象很深，是它列的翻车现场：

> 「报错你没看到嘛」「画面怎么黑了」「不要无视我的需求」「不用抱歉，帮我改对啊」「怎么切换页面后 css 失效了啊」

这几句几乎每一句我都说过。它们的共同点不是模型能力问题，是**缺少可验证的中间产物**。没有原型，你没法说「跟这张图不一样」；没有测试，你没法说「这里本来该报错」。

顺着这个思路，我把它压成三条谁也不许跳的红线：

**一、不跳原型直接改项目代码。** 视觉需求先进单文件 HTML，确认了再接入。

**二、没亲眼看到测试失败，就不算测过。** 这一条最容易糊弄。测试写出来直接绿，可能是它压根没测到东西。前端没有单测框架时，这件事降级成「可复现的验证步骤」：具体页面路径、具体操作、预期现象，一条条过。

**三、接新项目先摸坑，再写规范。** 原文有句话说得对：不要一上来就让它初始化。看不懂数据流就定规范，等于把错误固化下来，后面每一行代码都得遵守那个错误。顺序应该是先让它输出目录结构、模块依赖、核心数据流、构建与调试方式、已知坑点，形成一份「新人上手清单」，然后再谈规范。

整理完我把它固化成了一条固定的流水线：

```mermaid
flowchart LR
    A[定视觉方向] --> B[原型 HTML]
    B --> C[design.md]
    C --> D[需求对齐]
    D --> E[TDD 开发]
    E --> F[优化巡检]
```

前三步负责「想清楚长什么样」，后三步负责「确认了再动手」。中间 `design.md` 是分界线，写清色值、字阶、间距、组件圆角阴影，以后每做新页面先读它。它的意义是防止第五个页面跟第一个页面长得不像一家人。

## 一个提醒

工具层面我还做了一件事：把「装好了」这件事变成可验证的。

18 个技能，一个 `for` 循环跑过去，逐个校验目录名、`name`、`description`、首行分隔符，输出一张表。全绿才算装完。

这一步听起来多余，但第一条坑就是靠它才发现的。装完技能之后那种「应该能用了吧」的感觉，基本等于没验证。

另外试了一下其中带脚本的那个：`ui-ux-pro-max` 有一份本地 CSV 数据库和检索脚本，能搜风格、配色、字体搭配、组件模式。我实跑了一次，能出结果，而且支持 `--stack astro` 和 `--stack svelte`，正好对上这个站的技术栈。数据在本地，不联网。

## 还欠着的

**新技能需要重启才出现在列表里。** 我这边装完的当下是调不出来的，得等下一次会话。这个体验不太好，但没办法。

**分工那件事只做到一半。** 原文建议：顶模负责规划，低模按规范写码，顶模最后审查。我这个工具里做不到中途换模型，只能等价的退一步：先出计划再写代码，写完回头自己审一遍 diff。跳过自审是质量塌方的主要来源，这条比换模型重要。

**流程还没写进这个仓库的 `CLAUDE.md`。** 现在是挂在用户级配置里，对所有项目生效；要不要在项目规范里也落一份，还得想清楚它跟现有那 23 节怎么分界。视觉决策归流程，代码约定归 `CLAUDE.md`，两边不打架才好。

---

最后说个判断。这类「AI 工作流」的文章我读过一些，多数在讲提示词技巧。但我越来越觉得提示词不是瓶颈——真正决定产出质量的是**有没有中间产物可以互相验证**：原型对参考图，测试对预期，计划对设计。

流程的作用就是把「我觉得这样对」换成「你看这样对不对」。

这篇文章本身就是这么来的。
