# 一、项目背景、价值与架构（1–7）

### 1. 简单介绍一下这个项目

- **起点是真实痛点**：一个 Issue 从提出到关闭，要跨需求理解、改代码、PR 审查、CI 验证；判断一个 PR 能不能合，得同时看关联 Issue、diff、Review 评论、失败日志、当前代码和项目文档。
- **痛点本质**：信息散在 GitHub 各页面、本地仓库、团队文档里；每次同类问题都要重新找一遍证据；而且这事儿只有业务和代码都熟的人才干得了。
- **做了什么**：把这套判断链路串成 Agent 系统——同步 GitHub 关键数据 → 检索知识与当前代码 → 基于证据做 Issue 分诊、PR 审查、CI 排障。
- **边界**：评论、打标签、关 Issue 这类敏感操作**只生成草稿**，过权限校验和人工确认才执行。
- **定位一句话**：面向 GitHub 研发协作的全栈 AI Agent 系统，把分散的研发事实组织成可检索、可引用的证据。

### 2. 和普通 Coding Agent 有什么区别？

- **关注点不同**：Coding Agent 关注读代码、改文件、跑命令；这个项目关注**研发协作里的判断**（Issue 怎么分、PR 能不能合、CI 为什么挂）。
- **数据范围不同**：不只分析代码，还把 Issue、PR、Review、Workflow Run、日志、项目文档放在同一个仓库下一起看。
- **权限模型不同**：证据、权限、写操作确认单独处理。模型可以提建议，**但不能拿着 Token 直接对外执行**。

### 3. 整体架构怎么设计的？

按实际调用链讲，分五个部分（是为了讲清楚，不是代码里硬编码五个类）：

1. **前端**：Next.js。聊天、仓库数据、分析结果、执行过程展示。
2. **后端服务**：FastAPI。收请求、验参数权限、调功能、用 SSE 持续推进度。
3. **数据存储**：PostgreSQL 存 Issue/PR/CI/会话；Milvus 存文档向量；当前代码目录和代码关系支撑最新代码分析。
4. **Agent 与任务流程**：ChatAgent 理解问题选工具；Issue/PR/CI 三个专用 Agent 各管一摊；复杂问题由 Planner 拆、Observer 查漏、Synthesis 汇总。
5. **外部服务**：GitHub API、大模型接口、本地代码目录。改 GitHub 数据先生成草稿，确认后执行。

> **安全与 Eval 贯穿这五部分**——一个拦危险操作，一个检查改动后有没有变差。

### 4. 几个 Agent 怎么分工？

- **ChatAgent**：统一入口。理解意图、选工具、推进多轮、组织最终回答。
- **IssueAgent**：分类、优先级、复杂度、负责人建议。
- **PRReviewAgent**：审 diff、风险、阻塞项、测试建议。
- **CIDebugAgent**：定位首个错误、失败类型、修复方向。
- **跨领域问题**进多 Agent 工作流：Planner 拆 → 专用 Agent 分析 → Observer 查漏与冲突 → Synthesis 给最终答案。
- **不是为了堆数量**：每个 Agent 知道自己读什么、返回什么，能单独测试。简单问题仍然只用一个 Agent 或一个工具。

### 5. 你在项目里是什么角色？

- 从 0 到 1 独立实现。
- 动机是自己被这件事烦到：一个简单的 PR 审查要关联的信息太多，对业务不熟的同事很难胜任，大量时间耗在信息收集上。
- 所以工作之外自己做了这套东西，目标是**提高团队效率**而不是炫技。

### 6. 做得比较好的地方？

三点：

1. **不是套一个聊天框**。围绕研发流程解决真问题：Issue 分析、PR 审查、CI 排障各有对应 Agent，给的是可直接执行的建议。
2. **工程边界清楚**。历史文档走 RAG，实时代码直接查工作区（避免拿旧代码回答）；多 Agent 协作有超时、重试、停止条件、重新规划。
3. **写操作有安全闭环**。评论 PR、关 Issue 都是先出草稿，人工确认后执行，并留审计记录。

### 7. 现在做到什么程度？

- **已完成**：前后端可运行。GitHub 数据同步、读本地代码目录、RAG、Memory、ChatAgent 工具调用、三个专用 Agent、多 Agent 工作流、SSE 流式展示、操作确认、基础评测。主功能跑得通，有后端测试。
- **未完成（生产级）**：真实登录、团队间数据隔离、代码独立运行环境、服务重启后继续任务。
- **说法要点**：诚实区分「已实现」和「后续计划」，这在面试里是加分项不是减分项。

# 二、框架、模型与 Agent 基础（8–17）

### 8. Agent 是什么意思？

- 光有大模型只能「动嘴」：提示词写得再细，它也只能回答或建议，动手的还是你。
- **Agent 就是夹在用户和 AI 中间的那个程序**：接收指令，协调 AI 和实际工具去干活。
- 用「把 C 盘某个文件移到 D 盘并总结内容」举例，流程是：Agent 把请求 + 可用工具清单交给 AI → AI 说"调读文件工具，路径 X" → Agent 真去读 → 结果回给 AI → AI 判断下一步 → … → 最后 Agent 向用户汇报。
- 两个定义收尾：**Agent = 在 AI、工具、用户之间协调的程序；Tool = 提供给 AI 调用的函数。**

### 9. LangChain 是什么框架？

- 面向大模型应用开发的开源框架，解决模型、Prompt、消息、工具、检索器、输出解析器之间的**集成**问题。
- 统一封装各家模型的调用方式，能较一致地切模型、绑工具、组织消息。
- 提供 Tool Calling、RAG、结构化输出等组件，可做知识库问答、客服、数据分析、Agent 应用。
- **在本项目里**：用 `ChatOpenAI` 对接模型，用 `StructuredTool` 把 Issue 分析、PR 审查、CI 排查、RAG 检索、工作流注册成工具。
- **配上 LangGraph**：LangChain 管模型与工具集成，LangGraph 管有状态的执行流程（决策、调用、观察、循环、终止）。

### 10. 为什么选 Python / LangChain？

- **快速原型**：能快速验证想法。
- **社区资源**：示例和教程多。
- **生态熟悉度**：自己/团队熟悉 Python 相关库。
- **附加分答案**：技术选型要看团队栈、需求、性能、长期维护；也承认 Go 生态的 Eino 强类型更稳、Graph 编排效率高，在企业级生产落地有优势——**不是"Python 最好"，是"当前阶段最合适"**。

### 11. 用了哪些模型？为什么？

- **对话/Agent 主线**：DeepSeek V4 Pro（更适合复杂推理、Tool Calling、Agent 任务，国内友好）。走 OpenAI 兼容接口，换 `base_url` 可切其他兼容模型。Pro 比 Flash 贵，实际部署要按任务难度、延迟、预算权衡。
- **Embedding**：`Qwen3-Embedding-0.6B`，本地部署（公司内部文件属私域，DeepSeek 没公开 Embedding），1024 维。
- **Rerank**：`qwen3-rerank`。
- 也支持 DashScope 与 OpenAI 兼容的向量接口。

### 12. 为什么用这个模型？

- **国内、公司使用** → 优先国内模型。
- **Embedding 看 MTEB 榜**（业界较公认的多语言向量评测），阿里模型排名靠前 → 选阿里。
- **语言模型看成本、能力、国内友好度**三个维度 → 选 DeepSeek。

### 13. 详细说 ReAct

- 本质是 **Reasoning + Acting**：先思考、再行动，用多轮循环解决复杂问题。
- 用一个具体例子讲最清楚（问"地球和火星质量相加"）：先思考"我需要地球质量" → 调工具查地球 → 观察结果 → 再思考"还缺火星" → 调工具查火星 → 观察 → 再思考"该相加了" → 调计算器 → 观察 → 输出答案、循环终止。
- **一句话**：不直接瞎猜，先想该查什么，调工具，拿到结果判断够不够，不够继续查，直到能答。
- **优势**：实时决策、动态调工具。项目里用户问某个 req id 的 error 日志，就是 ReAct 拆步骤去调日志工具。

### 14. Plan-Execute-Replan 是什么意思？

- **结构化任务执行模式**：先规划步骤，再按步骤执行，随时校准方向。
- 三个角色：**Planner** 把模糊目标变成结构化步骤；**Executor** 只负责执行当前这一步，不管全局；**Replanner** 评估结果 → 有效就推进下一步，异常就调整计划，完成就终止返回。
- 经典例子是运维排障：Planner 先排"查日志 → 查监控 → 查历史工单"；执行第一步发现日志无异常 → Replanner 判断问题不在应用错误，**把监控提到第一步**；定位到某进程 CPU 95% → 再查该进程日志 → 发现全量同步未分页 → 根因明确，直接终止，不必跑完第三步。
- **两个优势**：结构化拆解（降低认知负荷）、动态适应（避免一条道走到黑）。

### 15. ReAct 和 Plan-Execute-Replan 的区别？

- **ReAct**：边想边做，没有固定步骤。
- **PER**：先拆步骤再执行，根据结果决定要不要改计划。
- **项目里怎么分**：对话场景用 ReAct（用户问题灵活，要实时决策，职责是开放式多轮咨询，执行链不预设很长）；运维/复杂排查用 PER（明确目标 → 多步骤计划 → 严格按计划调工具）。
- **关键补充**：两者**共享同一套工具集和知识库**，区别在工作模式和目标，不是两套系统。

### 16. 什么情况用 Prompt / RAG / 微调 / Workflow / Agent？

先判断"差在哪一层"：

| 需求特征 | 选什么 |
|---|---|
| 资料给全了，只要按格式分析 | **Prompt** |
| 需要查外部资料（文档、历史问题） | **RAG** |
| 步骤固定（生成草稿→查权限→等确认→执行） | **Workflow** |
| 下一步要看上一步结果才能定 | **Agent** |
| 有大量高质量样本、要稳定某类任务 | 微调（**本项目没做**） |

> 收尾要点：项目资料经常更新，所以更依赖检索和工具而不是微调；这几种可以搭配用。

### 17. 为什么用 SSE 不用 WebSocket？

- **SSE**：基于 HTTP，请求后连接不关，按 `text/event-stream` 持续单向推数据。
- **WebSocket**：独立协议，HTTP 握手后升级，全双工，双向随时发。
- **怎么选**：需要双向实时交互（聊天、协同编辑）选 WebSocket；只需要服务端单向推（行情、通知、AI 对话流）选 SSE。
- **本项目的理由**：只推 AI 生成的文本，不需要双向；SSE 更轻、基于 HTTP、后端实现和调试更简单。用户体验就是看一个人实时打字。

# 三、ChatAgent / Tool / MCP / Skill（18–32）

### 18. ChatAgent 怎么判断接下来做什么？

- **不是把所有决定都交给模型**。先用程序规则判断：能不能直接回答、要不要先读当前代码、要不要查记忆、是否需要同时调多个专用 Agent。
- 规则判断不了的，才交给模型选工具。模型拿到结果后判断资料够不够，不够继续查，够了给答案。
- **为什么这么分**：高风险操作（评论、关 Issue）不能让模型随便决定；普通问答又不能全写死。规则和模型各干各擅长的，系统才稳。

### 19. Agent 的 Prompt 怎么设计？

- 先说清**负责什么、不负责什么、最后要返回哪些字段**；再说能用哪些工具、什么时候必须先查资料、哪些操作必须用户确认。
- **两类 Prompt 分开**：ChatAgent 的 Prompt 讲工具选择与多轮推进；专用 Agent 的 Prompt 讲怎么分析 Issue/PR/CI 以及必须返回什么。不塞进同一段超长 Prompt。
- 读代码、查记忆、同时审 PR 和 CI、改 GitHub 数据这几类，**后端还写了固定规则**，不靠 Prompt 求模型自觉。
- **改完 Prompt 怎么验收**：重跑检查工具选对没、格式对没、答案有证据没、任务真完成没——不能只看几段回答感觉更自然。

### 20. Agent 是怎么实现工具调用的？

- **Function Call 之前**：工具描述写在 system prompt 里，完全靠字符串解析 → 经常出问题。
- 举反例：告诉模型有个查天气工具，参数是城市和日期；模型返回"调用天气工具，输入上海，明天"——**"明天"不是一个日期**，参数就错了。
- **有了 Function Call 之后**：工具描述从 system prompt 剥离，用 JSON 统一定义函数名、说明、参数字段，并规范回复格式。
- **收益**：开发者不用自己写解析和校验；格式错了模型侧能检测并自动重试，降低接入难度和 token 开销。

### 21 & 22. Function Call 的实现/执行流程

（这两题答案基本一致，答一次即可）

- **本质**：用 JSON 描述函数的名称、作用、参数。
- 调模型接口（如 `https://api.deepseek.com/chat/completions`）时，给 `tools` 字段按规范赋值。
- 返回消息里有 `tool_calls` 字段——代表模型选择了哪个工具。
- 程序按接口规范解析 `tool_calls` 就知道要不要调工具，**不需要再靠 prompt 解析字符串**。

### 23. 项目里有哪些 Tool？MCP 和 Skill 各是做什么的？

- **MCP 类比 USB-C**：电脑是 Agent，键鼠/U 盘/显示器是不同的 MCP Server；双方遵守同一协议就能即插即用。
- **MCP 的价值**：统一接入。同一个 Server 的 Tool 可被多个 Agent 用，不用每个项目重写连接代码。
- **本项目只把记忆做成 MCP Server**，提供三个 Tool（证据搜索、thread 上下文、会话事件）——**不是所有工具都走 MCP**，这点要说清。
- **ChatAgent 共 14 个工具**：覆盖记忆、当前代码目录、仓库状态、RAG、Issue、PR、CI、周报、安全检查、多 Agent 工作流。
- **一句话分工**：Skill 说明一类任务按什么步骤做，MCP 负责用统一方式把工具给到 Agent。

### 24. 谈谈你对 MCP 的理解

- USB-C 类比同上（电脑=Agent，外设=Server，接口=协议）。
- 换电脑或换外设，只要都支持同一标准就能即插即用。
- 落到 AI：**相同 Tool 可以给很多 Agent 使用，不需要重复写代码。**

### 25. MCP 工具具体怎么调用？和 Function Call 什么关系？

- 以记忆查询为例：后端先启动提供记忆工具的 MCP 服务，通过**标准输入输出**通信。
- 连接后先 `initialize` 交换协议版本和能力；用 `tools/list` 看有哪些工具、用途、参数。
- 调用时用 `tools/call` 发工具名和参数，服务查完返回，后端把结果交给模型继续回答。
- **FC 发生在模型这一侧**：把工具说明给模型，模型返回"我要调哪个、参数是什么"，程序检查后执行。
- **一句话切开**：**Function Call 解决"模型怎么表达调用意图"，MCP 解决"程序怎么连接和调用外部工具"。** 本项目只有部分记忆能力走 MCP，其他工具直接调后端函数。

### 26. 你知道 Agent Skills 吗？

- 来源：2025 年 10 月 Anthropic 推出，起初为提升 Claude 在某些任务的表现；因为好用，VS Code、Codex、Cursor 等迅速跟进；2025 年 12 月发布为**开放标准**，支持跨平台跨产品复用。
- **核心是渐进式披露**，三层：
  - **元数据层**：名称、描述，**始终加载**
  - **指令层**：`SKILL.md` 正文，**按需加载**，提供具体任务规则
  - **资源层**：Reference 和 Script 文件，**按需中的按需**
- **和 MCP 的区别**：

| | Agent Skill | MCP |
|---|---|---|
| 核心功能 | 教模型**怎么处理**数据（规则） | 给模型**供给**数据（连接） |
| 本质 | 结构化说明文档 | 独立运行程序 |
| 代码执行 | 适合轻量脚本、简单逻辑 | 安全和稳定更优，适合复杂任务 |
| 典型场景 | 格式标准化、规则校验、轻量自动化 | 数据查询、系统集成、复杂业务 |
| 加载方式 | 分层按需，省 token | 持续连接，实时取数 |
| 最佳实践 | 可与 MCP 组合：数据供给 + 规则处理 | — |

### 27. Skill 和普通 Prompt 有什么区别？

- 普通 Prompt 只是某次调用里的指令；Skill 是**可复用的一类任务处理规则**，不是把长 Prompt 换个文件存。
- **渐进式加载**：一开始只看名称和用途；真用到才读 `SKILL.md` 的步骤；步骤里需要参考或脚本才继续读。不用每次把所有说明都塞给模型。
- 本项目的 Skill 会写明名称、入口、包含哪些步骤、风险等级；系统启动时检查这些信息是否完整，所以 Issue 分诊 / PR 审查 / CI 排障的做法能分别维护。
- 一句话：**Prompt 是「这一次怎么告诉模型」，Skill 是「把一类任务的做法整理成可反复使用的说明」。**
- 🎯 **陷阱**：Skill 不能决定权限。真正改数据的操作仍要后端检查。

### 28. 工具越来越多，Agent 选错工具怎么办？

- 工具越多、名称和说明越像，越容易选错。
- 当前工具数量不大，且查记忆、读项目资料、同时分析 PR 和 CI 这几类常见问题，**先用程序规则定该走哪类工具**。
- **设计要求**：一个工具只干一件清楚的事，名称和参数要容易区分。别让三个工具都写"可以查询项目"。
- **验收方式**：用真实问题评测选错工具、漏调用、参数错误、多余调用——不是只看最终回答通不通顺。
- **扩到几十个工具怎么办**：先按问题挑出一小组候选，再让模型在里面选，不是一次全塞。

### 29. 如何保证不调错工具、不传错参数？

三层：

1. **工具描述精确**：功能、适用场景、参数格式、参数约束写细。例如日志工具要说明时间必须是 RFC3339、地域必须是枚举值。
2. **参数校验**：执行前做类型、范围、格式检查；不合法就把详细错误返回给模型让它重调。
3. **失败处理与次数限制**：按错误类型决定是否重试；反复调同一工具，达到最大步数或重复次数就强制停。

> 再加一层项目特有的：记忆查询、项目介绍、跨 Issue/PR/CI 审查会用**写死的规则**指定走哪类工具；改 GitHub 数据必须先生成草稿并由用户确认，**不能因为模型选中了工具就直接执行**。

### 30. Agent 执行异常/失败怎么处理？

- 典型异常是**无限调用工具、死循环**。
- **第一招**：设最大 Step，超了就强制中断。
- **第二招**：回头查 Prompt——是提示词写得有问题，还是模型本身选得不好。
- 补充：工具异常当 observation 回给模型，让它换策略或承认查不到，不崩进程。

### 31. 模型限流了，或向量数据库挂了，怎么处理？

- **先定位是哪一块出问题**，再决定还能不能给结果。
- **模型限流**：等一会儿重试，但限制重试次数；一直不通就结束这次请求，明确告诉用户服务暂时不可用——**不能让页面一直转圈**。
- **向量库挂了**：做了混合检索，Milvus 不可用时关键词检索还能跑就继续查；但资料不够时要老实说"目前无法判断"。
- **重排**：目前本地规则；接外部服务后要保留本地排序做退路。
- **有一类检查不能省**：权限检查和人工确认。不能因为服务异常就跳过，直接去发评论或关 Issue。
- **诚实收尾**：部分失败处理和检索降级已有，完整熔断、备用模型切换还没做完。

### 32. 介绍 IssueAgent / PRReviewAgent / CIDebugAgent

- **IssueAgent**：分类、优先级、复杂度、负责人建议、重复项、处理清单。解决"这件事是什么、谁来做、先不先做"。
- **PRReviewAgent**：结合改动和评论检查风险，问题分 P1/P2/P3，给出是否阻塞合并、该补哪些测试、是否建议合并。
- **CIDebugAgent**：从失败 Job/Step/日志里找首个关键错误，给失败类型、可能根因、相关文件、修复步骤。
- **共同点**：都有固定返回格式 + **一套不用大模型也能跑的基础规则**；模型结果还会再检查，不是生成一段文字就直接流转。

# 四、多 Agent 工作流与协作（33–41）

### 33. Multi-Agent 具体怎么实现？

按 `Planner + 专用 Agent + Observer + Synthesis` 组织：

- **触发**：用户问 PR 能否合并、有哪些阻塞项，或要综合 Issue/PR/CI/文档判断时，ChatAgent 调工程工作流。
- **Planner** 生成结构化 `WorkflowSpec`：任务目标、负责 Agent、任务依赖、允许的数据来源、验收条件、最大并行数、是否需要人工确认。
- **专用 Agent 分头干**：Issue / PR Review / CI Debug / RAG 检索 / Safety 检查。
- **统一返回结构**：执行状态、结论摘要、详细输出、证据数量、置信度、引用来源——下游直接读，不用解析自然语言。
- **Orchestrator 按依赖调度**：依赖完成的进待执行队列，相互独立的异步并行。例：仓库健康检查先跑，之后 PR 审查、CI 排查、RAG 检索并行。
- **失败处理**：记录错误类型，依赖它的后续任务标 `skipped`，避免下游在缺关键数据时还给结论。
- **Observer 统一检查**：证据是否充足、置信度是否过低、CI 与 PR 结论是否冲突、负责人是否真实存在于成员表、高风险操作有没有过安全检查。
- **有限重规划**：证据缺失/任务失败/置信度低 → Planner 按原因补任务（再检索一次、补 CI 分析、加安全审查），再跑一轮。
- **Synthesis 收口**：总体判断、任务图、阻塞项、证据来源、待确认问题、下一步操作。
- **全部落库**：执行记录、任务结果、工具调用、引用来源、耗时。方便查"这个结论来自哪个 Agent"。

### 34. 什么情况需要多 Agent？什么情况一个就够？

- **一个就够**：只需要一种证据 + 一个明确动作（查某个 Issue、解释一段日志）。
- **需要多 Agent**：跨多个领域、可以并行、需要不同输出标准、最后要处理冲突。PR 合并判断就是典型（同时涉及代码审查和 CI）。
- **代价要说清**：等待更长、费用更高、出错更难排查。所以**优先单 Agent，确实需要多种专业分析才启动工作流**。

### 35. 多个 Agent 之间怎么传任务和上下文？

- 通用做法是共享 Context：任务目标、执行计划、当前步骤、历史结果；各自读需要的信息，再把结果写回。
- 本项目也是这个思路，但**没让多个 Agent 自由聊天**：系统统一保存任务列表和执行结果——Planner 写计划，专业 Agent 写结果，Observer 和 Synthesis 读。
- 好处：每个 Agent 只做擅长的事；出问题能查清哪个任务用了哪些信息、返回了什么、最终结论怎么来的。
- 🎯 **陷阱**：任务计划里写"允许读哪些数据"只是**执行说明**，不代表 Agent 自动获得权限。真正读数据时后端仍校验仓库和用户权限。

### 36. 多个 Agent 怎么并行？

- Planner 先列出任务先后关系；系统每次找出"不需要等别人"的任务让它们同时跑，必须依赖前序结果的继续等。
- **并行数量有上限**，避免一口气发出太多模型请求、数据库查询、GitHub 请求，既提速又不压垮外部服务。
- **诚实交代**：当前都在同一个后端进程里跑，还不能分配到多台机器；服务重启后未完成任务不能自动续跑。

### 37. 多个 Agent 同时改代码，怎么避免文件冲突？

- 先声明：**DevFlow 设计上就不改代码**。它做分析给建议，改不改由开发者定，所以没有多 Agent 互相覆盖的问题。
- 如果要做，思路是：
  1. **先分任务**：前端/后端分开，同一个文件尽量指定一个 Agent 改，其他只给建议。
  2. **独立分支 + Worktree**：每人一份工作目录，先在自己目录里改，不覆盖别人。
  3. **统一检查合并**：两个任务都要改同一接口时，先定接口约定，或改成顺序执行。
  4. **合并后跑测试**：没有文件冲突不等于功能正常——后端改字段名、前端没跟着改，Git 不报冲突但页面会挂。

### 38. 上游 Agent 失败了，后面的任务怎么办？

- 依赖它结果的后续任务停止，标"已跳过"；无关任务继续跑。
- 会检查还能不能换方式补查；实在不行，**最终回答直接说明缺了哪些信息、哪一步失败**，而不是假装分析已经完成。

### 39. 多个 Agent 结论不一致怎么办？

- **不采用"最后一个 Agent 说了算"**。把结果放一起比较，重点看：严重代码问题、失败的 CI、Agent 自己也没把握的判断、互相矛盾的结论。
- **优先级规则**：明确的错误和真实证据优先。例：即使代码审查认为风险不大，只要 CI 还在失败，最终答案就不会建议直接合并。
- 证据不足就明说"暂时无法判断"或补任务。

### 40. 重新规划会不会一直循环？怎么停？

- 会有风险，所以必须有**次数 + 变化检查**。
- 默认最多重规划 1 次，配置上限 2 次。
- 如果没想到新检查步骤，或新计划和上一轮完全一样，**立即停止**，不重复执行相同任务。
- 到上限后保留已查到的结果，并明确告诉用户还缺什么、哪些暂时判断不了。

### 41. 服务重启后，执行到一半的任务怎么办？

- 现状：会保存聊天记录和任务执行记录，但**还不能自动续跑**，这块没做完。
- 要做的话：把任务拆步，每步完成就把结果和进度存下来（PR 分析完了、CI 还没分析，重启后知道下一步干什么）。
- **两个必须检查的点**：
  - 之前的结果还能不能用（PR 已经提交了新代码，旧审查结果可能得重做）。
  - **重复执行**：评论已经发出去了但没来得及记成功，重启再执行会多发一条。所以这类操作要单独记录，恢复时核对 GitHub 上的实际结果；能确认成功的跳过，确认不了的交给用户，**不能直接再发一遍**。

# 五、研发数据、RAG 与知识图谱（42–56）

### 42. 详细说 RAG

- **解决什么**：直接塞长文本受窗口限制，成本高、速度慢、准确率低。RAG 先检索再生成。
- **流程两段**：
  - 提问前（离线）：分片 → embedding → 存储
  - 提问后（在线）：召回 → 重排 → 生成
- **收益**：更准确、能追溯来源、能覆盖训练数据之外的新知识。
- **本项目的 RAG 范围**：Issue、PR、失败 CI 日志、项目文档、知识文件、人工确认的记忆。
- **两条铁律**：每次查询必须指定当前仓库（防串仓）；**当前代码不进向量库**，要分析代码就直接读工作目录，避免拿旧版本回答。

### 43. 为什么要同时做向量检索和关键词检索？

- **向量**擅长语义相近（换个说法也能召回）；**关键词**擅长错误码、文件名、Issue 编号、类名这类精确词。
- **融合分数**：0.62 向量 + 0.30 关键词 + 0.08 双路都命中。
- **诚实说明**：当前关键词主要看是否出现并给不同位置不同权重，还没用 BM25 这类专门算法；权重是初始设置，后面要用真实问题测了再调。

### 44. 文档怎么分块？Chunk Size 和 TopK 怎么选？

- **先按结构切，再用长度上限兜底**。Markdown/PDF/Word 尽量保留标题层级、自然段、页面信息；JSON/CSV 按字段或数据行；章节过长再按句子段落拆。
- **参数分类型**：知识库上传文档默认 `800 / overlap 100`；项目说明文档上下文更长，用 `1800 / 180`。
- **为什么要重叠**：让相邻块共享少量上下文。原因在上一段、方案在下一段时，能降低关键信息漏掉的概率。
- **TopK = 3**：指经过召回、融合、重排后最终交给模型的文档数。候选集会按倍数扩大，默认先拿 24 条，再重排保留最好的 3 条。
- **三个权衡维度**：相关答案能不能召回、排序是否合理、传给模型的上下文里有多少噪音。太小会漏，太大会引噪音并推高成本。
- **怎么证明**：项目有检索测试记录和 `Recall@K`、`Precision@K`、`MRR`、`NDCG`、RAGAS 等评测能力。
- **收尾话术**：这是工程基线，后续会补评测集再调分块、重叠和 TopK。

### 45. Embedding 是什么意思？

- 就是用专门的 Embedding 模型把文本片段转成向量。
- **为什么要转**：语义相近的文本，向量距离更近，方便做相似度匹配。
- 向量是"有大小有方向的量"，用数组表示，维度=数组长度。高维无法可视化但信息更丰富。
- 举例：语义相近的两句话会变成很相似的向量，无关内容则相差很远。
- 落点：大模型看不懂文字只能处理数字，Embedding 把语义变成可计算的向量，用户问题也转成向量，就能在海量片段里算相似度找最相关的。

### 46. 召回用的相似度算法是什么？

- 步骤：问题 → Embedding 成向量 → 与库里片段算相似度 → 取最相关的。
- **一般用余弦相似度**：算两个向量夹角的余弦值（-1 到 1），夹角越小越接近 1、越相似；只看方向不看长度，适合文本语义匹配。
- 还有欧式距离等，但语义匹配最常用余弦。

### 47. 向量数据库为什么用 Milvus？

- 先说清市面四类：关系型/列式数据库加向量插件（PG Vector）、传统倒排索引的 ES、基于向量库的轻量方案（Chroma）、专用向量数据库。
- **老实答**：当时是拍脑袋——搜"向量数据库"第一个就是 Milvus 官网；GitHub 42k star 说明社区活跃；案例里有很多大公司；而且 Eino 框架也提供 Milvus SDK，就选了。
- 🎯 这题**老实说**比编一套选型矩阵更讨喜，但可以补一句：现在会按规模、运维成本、过滤能力重新评估。

### 48. 召回与重排的区别？

- **召回**：快、便宜。问题向量化 → 与全库算相似度 → 挑 Top N（如 10）。**准确率有限，适合初筛。**
- **重排**：用专门计算文本对相似度的模型，逐对算问题与候选的相关性，从 10 里选 Top K（如 3）。**慢但准。**
- **为什么不直接召回 3 个**：召回是快而粗，重排是慢而精，两者结合是"先广撒网再精挑细选"，效果优于一步到位。

### 49. 知识库明明有答案却答错了，怎么排查？

**按链路一层层往前查，不要一上来就换模型：**

1. **先看这次实际查到了什么**，判断是"没找到"还是"找到了没用好"。
2. **入库层**：文件是否正常解析、切分、入库；文档更新了索引是不是还是旧的。
3. **召回层**：问题里有明确错误码，向量没找到但关键词能找到 → 检查两路配合是否正常。
4. **重排层**：正确片段是不是被排到后面了。
5. **压缩层**：是不是压缩时把关键内容删掉了。
6. **生成层**：资料完整交给模型还是答错 → 看 Prompt 和回答，判断是理解错还是漏了条件。
- **收尾**：修完把这个问题留下来，后面改检索或 Prompt 时再测一遍。

### 50. 如何避免大模型产生幻觉？（四层防护）

1. **强约束 Prompt**：明确"严格按文档内容回答，不用文档外信息"、"不知道就说不知道，不要编造"。
2. **RAG 增强**：召回片段明确标成"参考文档"，让模型基于它们回答。
3. **相似度阈值过滤**：设 0.8 的高阈值，低于就判定库里没有，直接告诉用户"知识库暂无相关信息"，**而不是让模型硬猜**。
4. **人工反馈闭环**：负反馈记录原因、`message_id`、`run_id`，可通知到群；通过轨迹接口分析——文档缺失就补文档，检索/Prompt 有问题就调策略，工具异常就修链路。

### 51. 怎么解决幻觉？

按手段分几大类：

- **引外部知识与工具**：知识库 + API 检索，多维度查真实数据。
- **微调**：只答指定类型问题，成本高、要大量高质量数据；可以用垂直行业微调模型降低成本。
- **多模型混用**：多模型同题对比，或一个答一个查。
- **后处理规则**：已知逻辑直接用程序验证（和多模型交叉验证类似）。
- **人工干预与反馈**：关键步骤让人选，人工进工作流。
- **优化提示词**：明确指令和上下文、引入假设约束、给背景信息、要求给来源、分步推理、限制输出范围、鼓励承认不确定、用反向提示排除内容。
- **温度**：调低更严谨，调高更发散。

### 52. 代码知识图谱解决什么问题？

- 解决「**一个文件和哪些 Issue、PR、CI、文档、代码符号有关**」，帮 Agent 从一个线索扩展到相关对象。
- 项目保存 `CodeSymbol` 和 `CodeRelation`，也会按明确字段和文本里的文件引用建立跨对象关系；查询时按有限深度看邻居。
- **局限要主动说**：目前还不能真正看懂所有语言的函数调用关系，很多关系是靠固定字段、文件名、文本引用找出来的；所以确认最新代码仍会去读 PR 对应的代码目录。

### 53. 文档更新 / 增量索引怎么做？

分成两条链路：

**A. 用户上传的知识文档**
- 元数据表记录：名称、存储路径、摘要、大小、处理状态、块数量、失败原因。
- 上传先算 **SHA-256**，仓库里已有相同内容的文件就直接复用记录，避免重复解析分块向量化。
- 状态流转：`queued → parsing → splitting → embedding → completed`。前端能看到进度，异常能看到原因并重跑。
- 重处理时按"仓库 ID + 文档来源 ID + 来源类型"删掉旧的块和向量，再重跑全流程。
- 现状：同名文件内容变了会作为新记录上传；要替换就删旧再传新。**后续计划**加稳定文档标识和版本关系，实现自动版本替换。

**B. 项目目录里的说明文档**
- 用 Git 提交 + 文件路径 + 最后修改时间 + 文件大小生成**项目指纹**。
- 每次检查索引状态重算指纹，变了就标 `stale`；重扫时只替换"项目文档"这一组索引，不影响其他知识来源。

**C. 执行方式**
- 上传接口先返回 `202` + 排队状态，解析/分块/向量化交给后台任务；用户可继续用其他功能，再看状态。
- 当前 `BackgroundTasks` 够单服务用；扩到多实例要迁到持久化消息队列，并补任务幂等、失败重试、超时恢复、任务监控。
- 不写死固定耗时，而是记录每步状态和失败原因，让任务可观察、可重跑。
- **下一步优化**：给每个块加内容摘要，只重新向量化变化的块，降低更新时间和向量模型成本。

### 54. PR 或文档更新之后，旧索引怎么办？

- 每份知识文档有"内容指纹"和来源。内容变了指纹变，就重新解析分块生成向量，并**删掉同一组旧数据**，避免新旧内容一起被搜出来。
- GitHub 数据重新同步后更新对应搜索数据；代码分析结果记录当时用的提交版本；用户问最新代码时仍直接读当前 PR 的代码目录。
- **诚实交代**：数据库和 Milvus 的更新还不能保证同时成功。更好的做法是后台先建一套完整新索引，确认无误再切换；失败就继续用上一版，避免搜到一半新一半旧。

### 55. 知道 Agentic RAG 吗？

- 普通 RAG：先检索，再把信息交给模型增强生成。
- **Agentic RAG**：不在回答前固定检索，而是在 ReAct 逐步推理过程中，由 Agent 决定**什么时候检索、怎么检索**。
- 本质上就是**把检索变成一个 Tool 交给模型**，让它自己选择调用。
- 本项目是**混合 RAG**：调用前的检索和推理中的检索都实现了。

### 56. 混合 RAG 有什么好处？

- Agentic 工具检索让模型自主选择文档搜索，非常灵活。
- 混合起来就同时拿到 **Agentic 的灵活性** + **普通 RAG 的质量控制**，适合要求高准确性的问答系统。

# 六、Memory 与上下文管理（57–64）

### 57. 多轮对话和上下文记忆怎么设计？

分层：原始消息 → 近期上下文 → 会话记忆 → 项目记忆 → 相关证据。

- **消息落库**：除了问题和回答，还记角色、仓库、会话 ID、路由结果、工具调用、Agent 执行事件，方便恢复完整过程。
- **近期上下文**：同会话按 `conversation_id` 查最近消息，解决"刚才那个 PR""前面提到的错误"这类指代。
- **每轮结束生成摘要 + 结构化记忆**：稳定事实、已做决策、未解决问题、后续任务、用户偏好、仓库上下文、引用来源；分别落到会话级和项目级。
- **组装 Prompt 时按预算来**：当前仓库、会话、压缩摘要、结构化记忆、上一轮摘要、相关证据、最近几轮原文。
- **为什么保留最近原文**：原文有准确措辞、代码片段、工具调用细节；较早历史逐步转摘要和结构化记忆控长度。
- **分阶段压缩**：估算 token，划分正常/预警/自动压缩/强压缩。预警时先轻压较早消息；压力继续增大就生成完整摘要，**同时保留最近 8 条消息**。
- 🎯 **压缩时必须保留工具调用和结果的对应关系**，否则模型看不懂这个结果来自哪次调用。
- **压缩边界**：压缩后插一条边界，后续组装从最近边界往后读，前面靠摘要和结构化记忆参与。
- **兜底**：摘要生成失败用抽取式摘要；连续多次失败触发熔断，避免每轮都重复失败。
- **超长项目历史**：按当前问题检索相关证据，只放和这次有关的 Issue/PR/CI/文档/历史决策。

### 58. 简单介绍 Memory 设计

- 多轮对话就是下次调用还能看到历史，看起来像有记忆。
- **分层**：最近几轮直接给模型保证连贯；更早压缩成会话摘要，只留重要问题、结论、待办。
- **要长期用的内容先进"待确认记忆"**，用户确认后才成为长期记忆并参与检索——避免模型把错误总结永久保存。
- 这些记忆也能通过 MCP 的记忆工具查询。

### 59. 哪些内容进长期记忆？为什么还要人工确认？

- **适合**：相对稳定、以后会复用——团队约定、已确认的技术决策、项目术语、长期任务背景。
- **不适合**：临时情绪、一次性猜测、未确认的负责人、很快过期的状态。这类先进"待确认"。
- **为什么必须人工批准**：长期记忆一旦写错，会在以后很多轮对话里反复影响答案，**风险比一次回答错误大得多**。

### 60. 短期上下文、长期记忆、RAG 的区别？

| | 是什么 | 生命周期 | 权威性 |
|---|---|---|---|
| 短期上下文 | 这一轮最近发生了什么 | 最短 | 可能只是用户假设 |
| 长期记忆 | 确认过、以后复用的项目事实/偏好 | 长 | 经过确认但可能过期 |
| RAG | 从大量外部资料里按问题临时找证据 | 每次临时 | 看来源和更新时间 |

- **分开存、分开组装**，就是为了避免一段聊天摘要被误当成仓库事实。

### 61. 对话超过窗口怎么办？

- **分层**：保留最近几轮完整对话，更早压缩成摘要，需要时再从长期记忆或向量库检索。
- 具体做法：先缩短过长的工具返回和重复信息，再生成历史摘要，**默认保留最近 8 条重要消息**；摘要尽量保留用户问题、关键事实、决定、任务、资料来源。
- **提前预警而不是等报错**：每次调用前估算长度，快到上限先压工具结果，还不够再总结更早对话。
- 🎯 **摘要会丢信息**：关键仓库事实和原始消息仍存数据库，需要核实要重新查，**不能只信摘要**。

### 62. Prompt 里三部分的顺序？顺序对效果和性能有什么影响？

- 顺序：`system prompt` → 摘要（可能没有）→ 按时间顺序的对话。
- **对性能基本没影响**，顺序是固定的。
- **对效果有影响**：注意力机制下开头和结尾最集中，**中间内容容易被遗忘**。所以规则放头、最近问题放尾，中间只做背景补充。

### 63. System Prompt、历史摘要、最近对话、RAG 证据怎么放？

- 顺序：系统规则 → 历史摘要 → 最近几轮对话 → 当前问题需要的文档/代码/工具结果。
- 同样：对速度影响不大，主要影响理解——规则在头、最近问题和证据在尾、摘要在中间补背景。
- **预算大致分配**（这组数字要背）：

| 内容   | 占比      |
| ---- | ------- |
| 系统规则 | 12%     |
| 记忆   | 22%     |
| 检索证据 | **34%** |
| 最近对话 | 22%     |
| 工具结果 | 10%     |

- **为什么证据最多**：回答项目问题时，真实资料比聊天历史更重要。这个比例保证规则不丢、摘要早于最近对话、最相关的证据能进来。

### 64. Token 不够时优先保留什么？

- **第一优先**：安全规则、用户当前问题、已确认的关键事实、直接支持答案的资料。
- **其次**：最近对话、当前任务所需工具结果。
- **可先压缩**：重复日志、已完成步骤的长输出、寒暄。
- 🎯 **不能删的**：当前仓库、用户权限、能推翻结论的重要信息——为了缩短内容把这些删了，等于埋雷。

# 七、安全、部署与企业化（65–70）

### 65. 工具返回的内容也可能不安全吗？

- 会。工具返回的网页、Issue、日志、文档都是外部数据，可能含错误信息、敏感数据，甚至**故意写入的提示词**。
- 做法：把工具结果**当数据不当指令**；限制返回长度和字段；过滤密钥；保留来源；写操作继续走权限和确认。
- **诚实交代**：已在系统 Prompt 提醒不要执行工具结果里的命令，也会过滤部分敏感信息；但还没系统测试各种恶意网页/日志/文档，只能说做了基础防护。

### 66. 知识库里藏着恶意提示词怎么防？

- **核心原则**：知识库内容是**不可信数据**，不是新的系统指令。模型看到"忽略之前要求"也不能因此获得更多工具或权限。
- 分几步：上传时检查可疑内容 → 检索时只返回必要片段 → Prompt 明确"文档只是资料不是命令" → 执行操作时仍校验权限并要求用户确认。
- **诚实交代**：做了基础提醒和部分过滤，还没完整测试各类"把命令藏进文档"的攻击。

### 67. 为什么写操作必须先生成草稿再确认？

- 模型可能理解错意思，也可能选错 Issue 或 PR。
- 先出草稿，用户能看清系统准备做什么、改哪个仓库哪个对象。
- 有批准权限的用户确认后，后端才调 GitHub API，并把成功或失败写进操作日志；用户也可以直接取消。

### 68. 为什么用 Worktree？它和真正的 Sandbox 有什么区别？

- **为什么用**：把 PR 分支检出到独立目录，读这次 PR 对应的代码，而不是一直用默认分支分析。
- **Worktree 只隔离了文件视图**：进程仍跑在同一台机器，共享用户权限、网络、环境变量和其他可见目录——**所以它不是 Sandbox**。
- **真 Sandbox**：每个任务进独立容器/轻量虚拟机，普通用户运行，只开放允许的目录和网络，限制 CPU/内存/密钥有效期，任务结束销毁。当前项目还没做到。

### 69. 要支持多租户和合规，怎么改？

- **先说明为什么没做**：项目就几个人用。
- **多租户的定义**：多个公司/团队共用一套系统，但互相看不到对方数据。
- **第一步**：给用户、仓库、对话、记忆、文档、Agent 运行记录、操作日志都打上"属于哪个团队"的标记。
- **第二步**：查询时后端按登录身份自动限制团队范围。数据库、Milvus、缓存、任务队列、日志**都用同一个范围**，模型不能自行修改。
- **更高要求**：可用独立数据库和独立密钥。

### 70. 怎么部署的？

- 就三块：向量数据库、前端、后端。
- 目前主要本地运行；Docker Compose 一份配置起数据库和 Milvus 所需服务，再分别启动 FastAPI 和 Next.js。
- 好处：办公网可直接用。

# 八、Eval、性能与项目复盘（71–77）

### 71. 项目的核心指标？

- **离线**：Agent Eval 的门禁通过率。
- **线上**：反馈覆盖率、负反馈率、反馈原因分布、未处理反馈数。
- **反馈机制**：每条回答都有"有帮助/没帮助"；负反馈可选原因（不准确、没解决问题、缺上下文、引用不可靠、工具异常）并可补充说明。
- **可追溯**：反馈关联 `message_id` 和本次执行的 `run_id`；配置飞书 Webhook 后负反馈会推送到群里（通知失败不影响入库）。
- **闭环**：用 `run_id` 调轨迹接口回溯路由、工具调用、Agent 事件、用户问题、最终回答、会话摘要，把问题归因为知识缺失 / 检索失败 / Prompt 问题 / 工具异常，并跟踪到解决。

### 72. 怎么评价一版 Prompt 写得好不好？

- **老实说**：刚开始时写得挺随意，导致回答不准、有幻觉。
- 后来去看 Prompt 工程文档，按治幻觉那套方案改（见第 51 题），跑出来就明显好了。
- **态度**：不装——"我本身不是专业搞这个的，主要精力在工作上，做这个项目是为了提效"。

### 73. Agent 的评测题怎么准备？让大模型打分靠谱吗？

- **先想清楚"什么叫答对"**：问 PR 能不能合并，不能只看回答写得好不好，还要看有没有查对应 CI、结论有没有依据。
- **题目来源**：项目里的典型问题 + 调试时遇到的错误（查错仓库、漏看失败日志、没资料还硬答，这些值得保留）。
- **每题除了问题，还要写**：应该查到什么、哪些行为不能出现。不要求和标准答案一字不差，但**关键事实和判断必须对**。
- **能程序检查的就别用模型**：工具有没有调用、字段有没有返回、有没有越权。
- **模型辅助判断的**：解释是否完整、有没有曲解资料；同时抽一部分自己看，检查模型打分是否合理。
- **诚实交代**：已有固定评测和评分功能，但题目覆盖够不够、模型打分与人工判断一致性还要继续验证。

### 74. 压力面：你们这个项目的 TPM 是多少？

- **不存在"硬答一个数"这条路**。
- 标准处理：坦白没听过这个指标 → 说明项目性质（为提效做的内部工具，不是面向海量用户的 ToC 产品）→ 表示这类专业测评还没做，后面会去了解。
- 🎯 压力面的核心考的是**抗压和坦诚**，不是知识面。

### 75. 回答太慢、Token 花太多，怎么优化？

- **先定位花在哪**：模型生成慢？工具调用慢？一个问题来回查太多次？
- **工具调用慢且无依赖** → 并行（PR 审查和 CI 分析数据备好就可同时做）。
- **模型读太多** → 清上下文：重复日志、无关文档、很早的闲聊没必要每轮都完整发；已有历史摘要和工具结果压缩。
- **反复调同一工具** → 查它为什么一直认为资料不够，调工具说明、Prompt 或停止条件。
- **简单任务换便宜模型** → 但要跑同一批问题验证效果没掉。
- 🎯 **别编百分比**：目前没做过大规模并发压测，所以用固定问题做前后对比，看耗时、Token、质量是否一起改善。

### 76. 压力面：项目看起来很简单，是很常见的方案？有深入的技术点吗？

- **策略**：这是压力面，**就顺着说、不要犟、不要心态崩**。考的是抗压。
- 话术：先认可对方视角（您资深，看这个当然简单），再讲自己的实际挑战（方案常见，但细节多，比如怎么解决幻觉）。
- 然后**把话题引导到自己准备最充分的地方**（幻觉治理、检索链路细节），掌握节奏。
- 🎯 关键心态：**承认方案常见不丢人，答不出细节才丢人。**

### 77. 最难的地方是什么？继续做会怎么改进？

**最难的四件事：**
- 让每个重要结论都能找到依据
- 让任务不会一直循环
- 让修改 GitHub 数据的操作必须经过确认
- 同时如实说明哪些做了、哪些只是计划

**一个重要取舍**：不把所有数据塞进向量库。最新代码直接读目录，Issue/PR/CI 状态查数据库，只有适合长期复用的知识进 RAG。代价是系统要先判断去哪查，好处是不容易拿旧代码或旧状态回答。

**继续做的优先级：**
1. 真实登录、团队数据隔离、密钥管理、防止 GitHub 操作重复执行
2. 长任务在服务重启后能续跑；为运行代码提供真正隔离的环境
3. 建立带标准答案的真实测试题，持续检查每次更新后效果有没有变差
